# Elmekawy Motion Studio

استوديو محلي لإنشاء وإدارة فيديوهات Motion Graphics باستخدام **Remotion + React + TypeScript**. يوفر واجهة عربية، معاينة حقيقية، تعديل النصوص والصور، حفظ المشروعات على القرص، وتصدير MP4 محليًا.

**الحالة الفعلية — 1 نوفمبر 2026:** يدعم التطبيق المشاهد المرنة التسعة، والفيديو والصوت وتايملاين التعليق والموسيقى والبرومبتات اليدوية والمقاسات الثلاثة ونسخ ZIP واسترجاع الإصدارات. تحكم صور V1/V2 متاح في نسخة مستقلة بالقالب `1.2.0` مع الحفاظ على النسخ القديمة. تفاصيل التنفيذ والتحقق في [PHASE_4_IMPLEMENTATION.md](docs/PHASE_4_IMPLEMENTATION.md).

## التشغيل السريع

المتطلبات الحالية: **Windows x64، Node.js 24 أو أحدث، npm، Git وGit LFS**. التصيير الحالي يستخدم Chrome وFFprobe المحليين لويندوز؛ دعم أنظمة أخرى يحتاج تجهيزًا منفصلًا.

عند تنزيل نسخة جديدة من GitHub:

```powershell
git clone https://github.com/M-Elmaghawry/Elmekawy-Motion-Studio.git
cd Elmekawy-Motion-Studio
git lfs install --local
git lfs pull
npm.cmd ci --ignore-scripts
npm.cmd run seed
npm.cmd run build
npm.cmd start
```

افتح **http://127.0.0.1:4311/**. اترك نافذة الخادم تعمل. في النسخة الحالية المثبتة والمجهزة، يكفي عادةً `npm.cmd start`.

### التشغيل بدبل كليك من غير VS Code

بعد التجهيز الأولي، افتح **[Elmekawy-Motion-Studio.exe](Elmekawy-Motion-Studio.exe)** من جذر مجلد المشروع. حجم النسخة المتحقق منها **21 KiB بالضبط (21,504 bytes)**. يشغّل الملف خادم Node.js مخفيًا، وينتظر جاهزيته، ثم يفتح الاستوديو في المتصفح الافتراضي. إذا كانت نسخة الاستوديو نفسها تعمل بالفعل، يفتحها دون تشغيل خادم إضافي.

عندما يبدأ الخادم من EXE، تظهر أيقونة بجوار الساعة: دبل كليك لفتح الاستوديو، وكليك يمين ثم **إيقاف الاستوديو والتصدير الجاري** لإنهائه. إغلاق تبويب المتصفح يترك الاستوديو يعمل. أمر الإيقاف يمر في قناة خاصة إلى الخادم، وينتظر حفظ حالة الرندر وإغلاق الخدمة؛ لا توجد نقطة إيقاف HTTP عامة، ولا يتم إيقاف خادم شُغّل خارج هذا الـLauncher.

اترك EXE داخل مجلد المشروع. لإنشاء مدخل على سطح المكتب، أنشئ **اختصارًا** للملف بدل نقله وحده. هذا Launcher للنسخة المحلية ويحتاج مجلد المشروع والحزم وNode.js 24+ وبيئة Windows/.NET Framework الموجودة بالجهاز. لا يحتوي على نسخة مستقلة من التطبيق أو Node.js، ولا يثبت أو ينزّل أي شيء عند فتحه.

المصدر في [tools/launcher/Program.cs](tools/launcher/Program.cs). إعادة بناء EXE باستخدام مترجم C# الموجود مع .NET Framework، دون SDK أو حزم إضافية:

```powershell
npm.cmd run launcher:build
npm.cmd run launcher:verify
```

اختبارات الـLauncher تعمل دون فتح متصفح أو إظهار أيقونة، وتستخدم بيانات معزولة للتحقق من التشغيل والإيقاف وإعادة الاستخدام وتعارض المنفذ. سجل بدء التشغيل موجود في `.studio/launcher/` وهو محلي وغير مرفوع إلى Git.

`npm ci` يحتاج الإنترنت لتثبيت الاعتماديات أول مرة. بعد تجهيز الحزم وملفات LFS، تعمل المعاينة والحفظ والتصدير محليًا دون اتصال بخدمة صور أو خدمة تصيير. `seed` يحافظ على المشروعات الموجودة، ويجهز الوسائط الافتراضية وينسخ متصفح Chrome الموجود أصلًا في V2 إلى التثبيت المركزي. تنزيل ZIP وحده قد لا يوفر محتوى LFS؛ استخدم Git LFS وتحقق من وجود ملف Chrome الحقيقي قبل التصيير.

للتطوير، أوقف الخادم الحالي ثم شغّل:

```powershell
npm.cmd run dev
```

واجهة التطوير: `http://127.0.0.1:5173`، وخادم API: `http://127.0.0.1:4310`. إعداد Vite يمرر طلبات التطبيق إلى الخادم. لا تشغّل خادمين يكتبان في مخزن المشروعات نفسه.

## إدارة المشاريع الحالية والمستقبلية

1. من **مشروع جديد** أدخل الاسم والعميل والهدف، واختر قالبًا متاحًا.
2. يولّد الخادم ID آمنًا وفريدًا، وينشئ المجلدات و`project.json` من تعريف القالب، وينقل الوسائط الافتراضية المطلوبة فقط.
3. من **المشاهد** عدّل النصوص، ومن **بيانات المشروع** عدّل الـBrief والسكريبت المرجعي.
4. من **الوسائط** ارفع الصور إلى الخانات المخصصة. لا يُنسخ كود التطبيق أو `node_modules` إلى المشروع.
5. راجع النتيجة مباشرة في Player، ثم احفظ. إعادة فتح المشروع تعيد تحميل البيانات المحفوظة.
6. صدّر MP4؛ تُحفظ نسخة ثابتة من البيانات لذلك التصدير، ثم نزّل الملف المكتمل من سجل الفيديوهات.
7. لإنشاء فيديو مشتق، استخدم **نسخ المشروع**: تحصل على بيانات ووسائط مستقلة، مع نفس المحرك والقالب المشتركين. لا يُنسخ سجل الرندرات إلى المشروع الجديد.

تغيير اسم العميل في الـBrief هو تعديل بيانات مرجعية؛ النصوص البصرية داخل الفيديو تُعدّل من حقول المشاهد. تغيير السكريبت المرجعي لا يعيد كتابة المشاهد تلقائيًا.

## القوالب وإصداراتها

| القالب | Composition ID | المدة | المشاهد | خانات النص في 1.1.0 | الصوت |
| --- | --- | --- | --- | --- | --- |
| `bim-personal-intro` — V1 | `ElmekawyBIMIntro` | 30 ثانية / 900 إطار | 6 | 51 | MP3 الأصلي بمستوى 0.3 |
| `bim-motion-study` — V2 | `ElmekawyBIMIntroV2` | 12 ثانية / 360 إطار | 5 | 60 | صامت |

كلاهما **1080 × 1920، 9:16، 30 FPS**. العدد يشمل النصوص التي تظهر فقط عند غياب صورة أو شعار. V2 يحتفظ بالرسوم التخطيطية الأصلية قبل/بعد إلى أن تُرفع الصورتان؛ رفع واحدة فقط لا يفعّل المقارنة المصورة.

- يرتبط كل مشروع بمعرّف قالب وإصدار محددين؛ لا يُخزّن `latest` في البيانات.
- `1.0.0` محفوظ للبيانات والمخرجات القديمة. `1.1.0` هو الافتراضي للمشروعات الجديدة، ويدعم تعديل كل النصوص.
- المشروعان العاملان رُحّلا إلى `1.1.0` في revision 2، مع الاحتفاظ بـrevision 1 في `history`.
- أي تغيير بصري أو تغيير في عقد القالب يُنشر بإصدار جديد. لا نعدّل قالبًا منشورًا لتعطيل قابلية إعادة إنتاج مشروع قديم.
- ترقية مشروعات أخرى تحتاج تحويلًا صريحًا يحافظ على القيم السابقة؛ لا توجد ترقية عامة تلقائية لكل أنواع القوالب.

لتحويل بيانات مشروع قديم `1.0.0` إلى حقول `1.1.0`، أوقف الخادم أولًا:

```powershell
node scripts/upgrade-text-editing.ts
npm.cmd start
```

السكريبت يرفض العمل أثناء تشغيل الخادم، يحفظ البيانات السابقة، ويحافظ على النصوص المعدلة، ويتخطى المشروعات التي رُقّيت بالفعل. `schemaVersion` للبيانات منفصل عن إصدار القالب، وما زال `1.0.0`.

## قاعدة إلزامية لأي قالب جديد: كل نص له خانة مستقلة

النصوص ليست Strings مجهولة موزعة داخل JSX. يعرّف القالب كل نص في [text-fields.ts](packages/shared/src/text-fields.ts) بمفتاح ثابت، وتسمية عربية واضحة، وقيمة افتراضية، ونوع عرضه.

مثلًا، مشهد البنية التحتية يفصل `infrastructure.eyebrow` و`infrastructure.title1` و`infrastructure.title2` و`infrastructure.title3` و`infrastructure.caption1` و`infrastructure.caption2`. تكرار كلمة `BIM` في مشاهد متعددة لا يجعلها حقلًا واحدًا.

المحرر يولّد الخانات من التعريف نفسه، والمحرك يقرأ القيم نفسها للمعاينة والتصدير. النصوص العامة في V2 تظهر في مجموعة مستقلة داخل كل مشهد، والنصوص البديلة في مجموعة موضحة. النص المطبوع داخل صورة لا يصبح نصًا قابلًا للتحرير؛ يُغيّر باستبدال الصورة.

عند إضافة قالب جديد يجب:

1. إنشاء مجلد إصدار جديد وتسجيل القالب وComposition والـmetadata المدعومة داخل المحرك الموثوق.
2. تعريف الحقول والأصول وتوقيت المشاهد والقيم الافتراضية، وتحديث الأنواع والتحقق والمخططات عند الحاجة.
3. ربط كل عنوان وسطر ورقم وتسمية مرئية بمفتاح مستقل؛ لا نستخدم النص الافتراضي نفسه كمفتاح مشترك.
4. التأكد من ظهور كل خانة في المحرر، وتأثير تعديلها في المشهد الصحيح، وحفظها وتصديرها.
5. مقارنة الشكل الافتراضي بالمرجع، واختبار الصور الغائبة وRTL والنص المختلط.
6. الاحتفاظ بالإصدارات القديمة، وكتابة تحويل بيانات منفصل إن كانت الترقية مطلوبة.

إضافة القوالب حاليًا عمل تطوير داخل المستودع؛ لا توجد شاشة لتوليد قالب أو مشاهد أو حركة تلقائيًا من وصف نصي.

## البيانات والتحقق والحفظ

`project.json` يجمع الهوية والإصدار والـBrief والقالب والفيديو واللغة وهوية العلامة والسكريبت والمشاهد والأصول والـPrompts والمراجع والصوت والإخراج وبيانات المصدر. الأنواع التنفيذية في [packages/shared/src/index.ts](packages/shared/src/index.ts)، والمخططات الفعلية في [packages/shared/schemas/v1](packages/shared/schemas/v1).

الخادم يتحقق بـAjv وبقواعد دلالية من الحقول المعروفة، وتوقيت القالب، ومراجع الأصول. الحقول التي يديرها الخادم مثل ID والإصدار والمسارات لا تُعدّل من طلب الحفظ العادي. الحفظ يستخدم كتابة JSON ذرية وقفلًا لكل مشروع، و`ETag` / `If-Match` لمنع تبويب قديم من الكتابة فوق إصدار أحدث. لا يوجد حفظ تلقائي صامت؛ احفظ التعديلات من الزر.

الأصول لها معرف وحجم وMIME وSHA-256. رفع البديل ينشئ ملفًا جديدًا بدل استبدال bytes التي يستخدمها رندر سابق. النسخ يشمل وسائط المشروع بصورة مستقلة، مع بقاء الموارد المشتركة مرجعية.

| `GET /ui-fonts/:family` | الخطوط المحلية المسجلة |
| `GET /engine/:hash/*` | ملفات بناء محرك مسموحة فقط |

الطلبات المعدّلة للبيانات تتطلب جلسة الواجهة المحلية والتحقق من Origin/Host. الرفع الحالي: **PNG / JPEG / WebP، ملف واحد حتى 50 MiB**، مع فحص النوع والـbytes وقابلية فك الصورة واسم تخزين مولّد. لا تُستخدم أسماء المستخدم كمسارات، وتُرفض محاولات traversal وUNC وADS والروابط التي تخرج عن المجلدات المسموحة. هذه واجهة محلية وليست خدمة عامة معدّة للنشر على الإنترنت.

## المعاينة والتصدير

Player يستخدم Composition والوسائط والخطوط المحلية نفسها التي يستخدمها Renderer. عند التصدير تُحفظ نسخة بيانات، ووصف مدخلات، وبصمة مصدر المحرك والقفل، ونسخة مصدر داخل `.studio/releases`، ثم ينفّذ عامل مستقل التصيير. طابور التطبيق يشغّل عملية تصيير واحدة في المرة، والتصيير الحالي يستخدم concurrency 2.

الحالات: `queued → bundling → resolving → rendering → verifying → completed`، مع `failed` و`cancelled` و`interrupted`. بعد إعادة تشغيل الخادم تُعلّم العمليات غير المكتملة بأنها متوقفة، وتبدأ المحاولة التالية كعملية جديدة. لا يتاح تنزيل ملف جزئي.

التصدير الحالي H.264 وCRF افتراضي 18 قابل للتعديل من 0 إلى 51. يُفحص الناتج بـFFprobe للتأكد من المقاس والإطارات والصوت. الإعداد المطلوب `yuv420p`، لكن FFprobe في البيئة الحالية يسجّل الناتج الفعلي `yuvj420p`؛ المانيفست يحفظ الطلب والواقع كلًا على حدة. V1 يحتوي على 30 ثانية فيديو؛ حشو AAC يجعل مدة الحاوية نحو 30.016 ثانية. V2 مدته 12 ثانية بلا صوت.

تثبيت الإصدارات ومصدر القالب والأصول وبيئة التصدير يساعد على إعادة الإنتاج. التطابق المطلق بين أجهزة وأنظمة مختلفة غير مضمون؛ الأدلة الحالية تخص بيئة Windows التي تم التحقق عليها.

## توليد الصور والـPrompts

العملية **يدوية بالكامل**: يكتب المستخدم Prompt أو يستخدم قالبًا نصيًا محفوظًا، ينسخه، ويفتح موقعه الخارجي بنفسه، ثم يولّد الصورة وينزّلها ويرفعها إلى الاستوديو.

التطبيق يخزن ويعرض وينسخ الـPrompts فقط. لا يحتوي على نموذج يكتبها تلقائيًا، أو API لتوليد الصور، أو MCP للصور، أو أتمتة متصفح، أو اشتراك مدفوع متصل. المراجع لا تُجلب تلقائيًا من الإنترنت. أي قدرة إضافية تحتاج قرارًا وربطًا صريحًا لاحقًا.

## ما يدخل GitHub

هذه النسخة تحفظ كود الاستوديو والقوالب والمخططات والتوثيق والأصول والخطوط وبيانات المشروعات وسجلها والرندرات، والمجلدين الأصليين والنسخة الاحتياطية الكاملة، وسجلات jobs ونسخ مصدر التصدير وتقارير QA. تشمل أيضًا EXE التشغيل ومصدر C# وسكريبت إعادة بنائه والتحقق منه. ملف Chrome التاريخي الكبير محفوظ بـGit LFS، والنسخة الموجودة في الأرشيف تشير إلى محتوى LFS نفسه.

حسب طلب مالك المشروع، يشمل الرفع **كل ملفات مساحة العمل**: المكتبات `node_modules`، والبناء `apps/studio/dist`، والكاش، ونتائج الاختبارات، وبيانات المشروعات المحلية، والأصول والأرشيفات. ملف `.gitignore` الرئيسي لا يحتوي قواعد استثناء. مجلد بيانات Git الداخلي تديره Git نفسها.

استخدم الأمر التالي للرفع الكامل على الفرع الحالي؛ يضيف الملفات حتى لو غطتها قواعد تجاهل داخلية أو عامة، ويسجل الملفات بحجم 50 MiB فأكثر باستخدام Git LFS، ثم يتحقق من تطابق النسخة البعيدة:

```powershell
npm.cmd run github:sync -- "Sync complete project workspace"
```

يمكن إضافة `--dry-run` لفحص عدد الملفات وحجمها والملفات التي تحتاج Git LFS قبل الرفع. يتطلب الرفع الكامل تثبيت Git LFS.
